# 第 18 版：启动守护、DNS 缓存刷新与恢复耗时优化

基于第 17 版和已在路由器验证的局部修复整理。构建结果以 GitHub Actions 为准，源码 ZIP 不能刷入路由器。

## 本版修改

- 修复看门狗启动顺序：START=99，排在代理服务之后；迁移旧 S100 链接。首次启动最多 180 秒宽限，就绪后仍正常检测故障。
- DNS 候选配置在同一次应用中只生成和验证一次；保留 DNS/Xray 预检、故障转发保护和就绪检查。
- DNS 缓存刷新按实例 PID 校验主进程后发送 HUP，避免临时子进程退出造成 killall 误报；任一实例失败不写成功标记。
- 同一次 restart 中，防火墙首次安装成功且期望规则、实际内核表及策略路由一致，才复用；检查失败或状态变化仍完整安装。不做跨操作缓存。
- 最近代理探测与历史守护事件分开显示。探测日志保留最近 10 轮，包含返回码、HTTP、计时和节点/PID 信息；缺少运行确认时标记不确定。
- 自动恢复单独记录阶段耗时，保留本次与上次记录，避免被手动应用覆盖；日志保存在内存，重启清空。
- ZeroTier 防火墙默认 mangozt 入站 ACCEPT、出站 ACCEPT、转发 REJECT，LAN 到 mangozt 允许；开启 IPv4 动态伪装，伪装源/目标网段留空。管理入口仍是防火墙页面。
- 保留第 17 版节点编号、最近 10 条可下载节点日志、统一订阅输入、备用节点逐个检查、GFW DNS 修复。

## 验证与边界

- 局部脚本已经过真实路由器 BusyBox 隔离测试和在线验证；防火墙复用一次实测重启 44.37 秒，Google HTTP 204。此前约 53 秒记录负载不同，不保证固定提速。
- 冷启动守护修复后能自动开始探测，但启动慢、全部候选失败时恢复耗时偏长的问题尚未完全解决。
- 所有候选失败时仍可能重启当前节点；尚未实施“核心健康时仅退避、减少重启”的新策略。
- 候选端口连通不代表 VLESS 认证成功；监听就绪不代表互联网可用。并非无缝切换，没有完整应用事务回滚，也未增加 IPv6 透明代理。
- 已排除实机未通过的旧进程交接实验，以及因完整程序摘要超过 55 秒而放弃的配置校验缓存实验。不会把这些实验打入本版。
- 完整新 BIN 尚需本次云端构建、容量与实际 MIPS 配置验证；刷入后的冷启动和长期稳定性仍需验证。

## 日志

- `/var/etc/mango/probe-history`：最近 10 轮代理探测。
- `/var/etc/mango/node-history`：最近 10 条节点切换记录。
- `/var/etc/mango/apply-timing`：最近一次启动/应用阶段耗时。
- `/var/etc/mango/recovery-timing` 与 `.previous`：最近两次自动恢复阶段。

## 构建与使用

设备：GL-MT300N-V2。使用固定 OpenWrt 25.12.5 源码，Xray 26.3.27；版本与规则摘要见 scripts 中的构建脚本。

Actions 工作流先验证源码，再编译、检查容量与 MIPS Xray 配置；成功产物包含 sysupgrade.bin、SHA256SUMS 和本说明。固件默认直连、自动切换关闭，不包含个人节点、订阅凭据或 ZeroTier 身份。

刷机前备份当前配置；保留旧配置刷入时，旧的用户配置可能覆盖本版默认防火墙设置。仅刷 sysupgrade.bin，不刷源码 ZIP。
